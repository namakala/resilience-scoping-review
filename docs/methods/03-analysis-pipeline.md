# Sequential Analysis Pipeline

The thematic analysis was executed as a sequential pipeline comprising ten discrete stages. The pipeline advanced from data loading through embedding generation, lexical indexing, code inference, code review, theme inference, theme review, interpretation synthesis, interpretation review, and final export. Each stage was dispatched by a central runner that delegated to specialised service modules for embedding computation, LLM batch inference, human-in-the-loop coordination, and result serialisation. Stage progression was governed by a state machine that verified dependency satisfaction before advancing, and revisiting an earlier stage triggered selective recomputation of all downstream stages affected by the change.

The first three stages established the analytical substrate: exemplar and ontology data were loaded from Parquet storage, vector embeddings were generated for all exemplars and keywords, and the BM25 lexical index together with the ontology graph and traversal caches were built. Stages four through nine formed the core iterative loop of inference and validation: codes were inferred from exemplars via large language model (LLM) batch calls, reviewed by the researcher, themes were inferred from approved codes, reviewed, and interpretations were synthesised from approved themes across ontology branches, then reviewed. Each inference stage depended on the completion and approval of the preceding validation stage, creating a strict sequential dependency that preserved analytical coherence.

Workflow state was persisted as a serialised JSON object in a DuckDB session table, recording the current stage index, dirty flags per ontology tag, checkpoint timestamps, configuration version hash, and cumulative action count from human-in-the-loop interactions. On startup, the pipeline detected existing session state and offered to resume from the last checkpoint, enabling long-running analyses to survive process interruptions. The state machine validated configuration version consistency before resuming to prevent silent drift between the analysis configuration and previously computed artifacts.

A dirty-state propagation mechanism governed incremental recomputation across the pipeline. Each ontology tag maintained a dirty flag that was set to true when any of its constituent codes, themes, or interpretations were edited or invalidated. When the pipeline reached a given inference stage, only tags marked as dirty were processed; clean tags were skipped entirely, resulting in zero LLM calls and minimal computational overhead. This selective execution strategy ensured that edits to individual semantic entities did not cascade into full re-analysis of the entire corpus.
