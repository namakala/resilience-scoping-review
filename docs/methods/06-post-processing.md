# Constraint Validation and Data Export

Structural constraints were enforced at three validation points across the pipeline: during batch inference after LLM output parsing, during human-in-the-loop review before mutation execution, and during persistence operations at the graph CRUD layer. Six constraint rules governed well-formed ontology evolution: each code could belong to at most one approved theme; each theme must contain at least two codes sharing the same parent tag; each theme could belong to at most one approved interpretation; each interpretation must span a contiguous tag subtree; all tag assignments must reference existing ontology nodes; and no merge operation could introduce cycles into the directed acyclic graph. Constraint violations blocked persistence at the violating action and returned descriptive error messages with remediation suggestions.

The contiguity constraint for interpretation tag spans was enforced through a dedicated algorithm that verified the set of spanned tags formed a connected sub-DAG using lowest-common-ancestor and shortest-path computations. Theme approval additionally verified that all constituent codes had been individually approved during the preceding code review stage, creating an implicit dependency chain that prevented orphaned inferences. The constraint system was implemented as self-contained rule functions dispatched by action type, enabling independent testing and future extension without modifying the core validation logic.

The export stage serialised all approved semantic entities into three output formats at the conclusion of the pipeline. A hierarchical JSON structure preserved the full ontology tree with nested codes, themes, and interpretations under their respective tags, including supporting evidence citations and status metadata. A flat CSV format provided tabular output suitable for quantitative analysis of code and theme distributions across tags. A Markdown report presented the analysis results in human-readable form with tag-level summaries and narrative descriptions of each interpretation.

Session state was persisted throughout the pipeline lifecycle to support incremental execution and recovery from interruptions. The state object recorded the current pipeline stage, dirty flags per ontology tag, configuration version hash, and user action count in a DuckDB session table. Each stage checkpoint wrote the current state synchronously, enabling the pipeline to resume from the exact point of interruption on restart. The configuration version hash was compared on resume to detect changes in analysis parameters that might invalidate previously computed artifacts.
